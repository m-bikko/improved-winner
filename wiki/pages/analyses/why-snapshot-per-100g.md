# Почему снимок КБЖУ хранится на 100 г

## Задача

Запись дневника не должна меняться задним числом, если кто-то исправил
калорийность продукта в справочнике. Иначе правка одной цифры перепишет
статистику за все прошлые месяцы.

## Варианты

**1. Хранить только ссылку на продукт.** Отпадает сразу: любая правка
справочника переписывает историю.

**2. Хранить абсолютные значения за порцию.** Кажется очевидным: записали
«150 г = 170 ккал» и всё. Ломается на первом же редактировании: чтобы
пересчитать «было 150 г, стало 200», нужно знать калорийность на 100 г —
а её в записи нет, значит придётся идти в живой продукт. Который мог
измениться. То есть история поедет ровно там, где мы её защищали.

**3. Хранить снимок на 100 г плюс граммы.** Правка граммовки считается
из снимка и остаётся честной. Абсолютные значения получаются генерируемыми
колонками, так что суммы по дню база отдаёт готовыми.

## Решение

Вариант 3.

```
grams          200
kcal_100       100   ← снимок, заморожен
kcal           200   ← generated always as (grams * kcal_100 / 100)
```

## Проверка

`scripts/check-history.ts` прогоняет сценарий целиком в транзакции:

1. Запись 200 г при 100 ккал/100 г даёт 200 ккал.
2. Продукт в справочнике меняется на 200 ккал/100 г — запись остаётся 200 ккал.
3. Граммовка меняется на 300 — выходит 300 ккал, а не 600. То есть пересчёт
   пошёл по снимку, а не по живому продукту.
4. Архивация продукта не рвёт запись.

## Цена решения

Дублирование данных: КБЖУ каждого продукта лежит в каждой записи дневника.
При тысячах записей это десятки килобайт — несопоставимо с ценой испорченной
истории.
