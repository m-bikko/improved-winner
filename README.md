# Тандем

Приватное PWA на двоих: общие разделы пары, дневник питания с базой продуктов,
цикл и подготовка к малышу. Mobile-first: четыре главных раздела в нижней панели
вкладок, остальные - в «Ещё».

Пользователей двое. Третий, необязательный аккаунт - повар: он видит только дневник
владельца и справочник продуктов. Интерфейс на русском, казахском и английском.

Стек: React 19, Vite, TypeScript, Tailwind CSS v4, TanStack Query, motion, Leaflet.
Данные, вход и рассылки - Supabase. Хостинг и функция отправки push - Vercel.

он так устроен - в `wiki/index.md`.

## Название и знак

Название задаётся **при сборке**, а не в настройках:

```
VITE_PUBLIC_APP_NAME="Тандем"          # заголовок, манифест, шапка
VITE_PUBLIC_APP_SHORT_NAME="Тандем"    # подпись под иконкой
```

Пусто - «Тандем». В коде название есть только в `src/lib/appName.ts`,
`vite.config.ts` и `index.html`; в базе его нет вовсе.

Настройки в профиле для этого нет намеренно: **iOS запоминает имя и иконку
в момент добавления на экран «Домой»** и больше их не перечитывает.
Переключатель менял бы надпись внутри приложения, а подпись под иконкой
оставалась бы старой. После переименования на телефоне нужно удалить иконку
и добавить заново.

Что от названия **не** зависит и при переименовании не меняется: ключи
localStorage (`love-promises-auth`, `love-promises-outbox`) и адреса аккаунтов.
Это опознаватели живых данных - тронуть их значит разлогинить обоих и потерять
очередь неотправленных записей.

Знак - `pnpm tsx scripts/make-icons.ts`. Скрипт пишет и `public/favicon.svg`,
и все PNG из одного контура; править favicon руками не нужно. Текста в знаке
нет, поэтому смена названия перерисовки не требует.

## Быстрый старт

```bash
pnpm install
cp .env.example .env    # заполнить кредами проекта Supabase
pnpm db:push            # применить миграции
pnpm bootstrap          # создать аккаунты пары
pnpm dev
```

Повар заводится отдельно и только если нужен:

```bash
pnpm tsx scripts/bootstrap-cook.ts
```

Скрипт создаёт аккаунт со случайным паролем, по которому войти нельзя. Рабочую ссылку
выпускает владелец в профиле приложения, и показывается она один раз.

В `.env.example` только то, что нужно для входа. Переменные для уведомлений описаны
в разделе «Уведомления» ниже.

## Восстановление доступа - прочитай до того, как понадобится

Аккаунты живут на **синтетических адресах** (`bikosh@lovepromises.app`,
`aminosh@lovepromises.app`). Почты за ними не существует, поэтому письмо
«сбросить пароль» отправить некуда. Кнопки «забыли PIN?» в приложении нет и быть
не может.

Единственный путь при забытом PIN или сломанной сессии:

```bash
# в .env поправить LOVE_PIN_BIKOSH / LOVE_PIN_AMINOSH на новые значения
pnpm bootstrap
```

Скрипт идемпотентен: он не создаёт дублей, а приводит существующие аккаунты
к состоянию из `.env`, в том числе перезаписывает PIN. Работает через Admin API
с секретным ключом, то есть только с машины, где лежит `.env`.

PIN можно сменить и из приложения - «Профиль → Сменить PIN», но это требует
живой сессии.

## Команды

| Команда | Что делает |
|---|---|
| `pnpm dev` | Дев-сервер |
| `pnpm build` | Продакшн-сборка (сначала проверка типов, в том числе `scripts/`) |
| `pnpm preview` | Посмотреть собранную версию |
| `pnpm typecheck` | Только проверка типов |
| `pnpm db:push` | Применить миграции к проекту из `.env` |
| `pnpm db:types` | Перегенерировать `src/types/db.ts` из схемы |
| `pnpm bootstrap` | Создать или починить аккаунты пары |
| `pnpm sql "<SQL>"` | Выполнить SQL от имени postgres (в обход RLS) |
| `pnpm secrets` | Положить серверные секреты из `.env` в Vault |

Перед коммитом - `pnpm build`, а не только проверка типов `src/`: на Vercel падает
именно сборка, и она типизирует ещё и скрипты.

После изменения схемы - `pnpm db:types`, иначе `src/types/db.ts` разойдётся с базой.

## Проверки

В `scripts/` 62 проверки `check-*.ts`, по одной на раздел или инвариант. Запуск одной:

```bash
npx tsx scripts/check-schema.ts    # инварианты схемы - каждый кейс обязан упасть
```

Все разом:

```bash
for f in scripts/check-*.ts; do npx tsx "$f" > /dev/null 2>&1 || echo "ПРОВАЛ $f"; done
```

Что важно знать:

- **Проверки ходят в базу из `.env`, то есть в настоящий проект.** Те, что построены
  на `scripts/harness.ts`, выполняются в одной транзакции и откатывают её в конце.
  Уведомления внутри успевают только встать в очередь `pg_net` и исчезают вместе
  с откатом, поэтому никому ничего не приходит.
- **`check-push.ts` нужен `PUSH_SHARED_SECRET` в `.env`.**
- **На локальном стеке больше половины проверок падает.** Там нет отправки уведомлений
  и серверных секретов, и интерфейс тут ни при чём. Проверки гоняются против `.env`.

## Локальный стек и проверки в браузере

Для сценариев, которые создают и удаляют данные, есть локальный Supabase
(`supabase start`, адреса в `.env.demo`). Настоящие данные он не трогает
и уведомлений не отправляет.

```bash
TANDEM_ENV_FILE=.env.demo pnpm db:push                       # миграции на локальный стек
TANDEM_ENV_FILE=.env.demo npx tsx scripts/qa/seed-local.mjs <ГГГГ-ММ-ДД>   # наполнить длинными строками
pnpm dev --mode demo --port 5199                             # приложение на локальной базе
```

Сценарии в `scripts/qa/`. Первым трём нужен запущенный дев-сервер на порту 5199:

| Скрипт | Что делает |
|---|---|
| `e2e.mjs [адрес] [папка] [раздел]` | Жесты через настоящие касания и запись в базу |
| `login-cook.mjs [папка]` | Вход по PIN и режим повара |
| `walk.mjs <адрес> <папка> [light\|dark] [ширина] [фильтр]` | Обход всех экранов: переполнение, мелкие цели, ошибки страницы |
| `sheet.mjs <папка> <файл> <png...>` | Контактный лист из скриншотов, по 6 в ряд |

Playwright сценарии берут из установленного скилла `playwright-skill`, в зависимостях
проекта его нет. `seed-local.mjs` и `scripts/seed-demo.ts` отказываются работать
не на localhost.

## Решения, о которых стоит знать заранее

**Снимок КБЖУ в дневнике хранится на 100 г, а не абсолютом за порцию.** Иначе
поправить граммовку задним числом можно было бы только сходив в живой продукт,
а он мог измениться - и история поехала бы ровно там, где её защищали.
Проверяется `check-history.ts`.

**Норма дня тоже замораживается.** Она выводится из веса, а вес меняется:
без снимка похудение переписывало бы уже закрытые кольца - день, закрытый
на 95%, через месяц стал бы перебором. Сегодня считается живьём, прошлое
читается из `daily_goals`. Проверяется `check-goal-history.ts`.

Отсюда общее правило: **если число выводится из чего-то меняющегося,
а показывается в контексте прошлого - его надо замораживать.**

**Инварианты держит база, а не форма.** Всё, что должно быть правдой всегда,
выражается ограничением в схеме. Например, блюдо не может быть ингредиентом
другого блюда - это запрещено составными внешними ключами на `foods(id, kind)`.

**Дату дня считает клиент.** Часовой пояс базы - UTC, поэтому никаких
`current_date` и `now()` для определения дня: еда в 21:00 по Алматы уехала бы
на завтра. В `src/lib/date.ts` нет ни одного `toISOString()` - он тоже отдаёт
UTC.

**КБЖУ блюда считает вью `foods_v`, а не триггер.** Триггер на `foods` UPDATE,
апдейтящий `foods`, вызывал бы сам себя. Вью снимает и рекурсию, и риск
рассинхронизации.

**Поиск разный для разных данных.** Продукты ищутся на клиенте (мгновенно,
работает офлайн), темы - через FTS на сервере. Подробности и границы -
в `wiki/pages/concepts/search.md`.

**Фотографии продуктов ужимаются на клиенте до 512 пикселей и WebP** -
5.5 МБ снимок становится 41 КБ. Потолок стоит и в клиенте, и на самом бакете:
клиент можно обойти. Перекодирование заодно выбрасывает EXIF с координатами
съёмки. Подробности - `wiki/pages/concepts/photos.md`.

**Данные в кэше TanStack Query обязаны переживать JSON.** Кэш сериализуется
в IndexedDB: `Map` восстанавливается пустым объектом, `Date` - строкой. При
несовместимом изменении формы кэша нужно поднять `CACHE_BUSTER`
в `src/lib/queryClient.ts`. В режиме разработки нарушение ловит проверка
в самом `queryClient` - на этих граблях я стоял дважды.

**Базовые CSS-сбросы лежат в `@layer base`.** Неслоёные правила в каскаде
побеждают любой `@layer`, поэтому `button { background: none }` на верхнем
уровне перебивал бы утилиты Tailwind.

**Интерфейс устроен как системное приложение iOS.** Системный шрифт, плоские группы
без теней, один акцентный цвет - только на том, что нажимается. Цвета, радиусы и шкала
шрифтов заданы токенами в `src/index.css` через `@theme`, поэтому общий вид меняется
в одном месте, а не в каждом экране. Подробности - `wiki/pages/concepts/visual-language.md`
и `wiki/pages/concepts/design-system.md`.

**Кнопка «Обновить» видна в шапке каждого экрана.** Потянуть экран вниз - второй
способ, а не замена: жест сам никто не найдёт.

**Тексты на трёх языках.** Источник - `src/lib/i18n/ru.ts`, из него выводится тип
ключа, а `kk.ts` и `en.ts` обязаны покрыть его целиком: пропущенный перевод ломает
сборку. Уведомления собирает база, и приходят они на языке получателя.
Подробности - `wiki/pages/concepts/i18n.md`.

**Карта мест работает на бесплатных сервисах OpenStreetMap, без ключей.** Тайлы
`tile.openstreetmap.org` и публичный геокодер Nominatim запрашиваются прямо из браузера.
У Nominatim лимит - запрос в секунду на всё приложение и запрет подсказок при вводе,
поэтому поиск идёт по кнопке через очередь с кэшем. Тайлы запрещено предзагружать,
и service worker их не сохраняет. Лимиты и что делать при блокировке -
`wiki/pages/entities/places.md`.

## Уведомления

Два канала - push и Telegram. Решает «кому и что» база: триггеры на событиях
и задания `pg_cron` по расписанию.

- **Telegram** шлёт сама база через `pg_net`: токен бота нельзя отдавать в браузер.
- **Push** требует серверного кода - `api/push.ts` на Vercel. Подписать VAPID
  и зашифровать нагрузку из plpgsql нельзя. База решает «кому и что», функция -
  «как».

Расписание живёт в базе, а не в Vercel Cron: на Hobby у того лимит в один запуск
в сутки. Большинство заданий идёт раз в час, срочные - чаще: сроки задач и лекарства
проверяются раз в 5 минут. Задания по местному времени сверяют его по часовому поясу
каждого профиля, поэтому одно расписание покрывает любые пояса.

**Адресат зависит от вида.** О своём действии уведомлять незачем: получать пуш
о собственном комментарии - верный способ отключить уведомления в первый день.
О действии второго узнаёт партнёр, о сроке общей задачи - оба, о пустом приёме
пищи - только сам человек. Отсюда три функции: `tg_notify_self`,
`tg_notify_partner`, `tg_notify_both`.

**Каждый вид рассылки выключается отдельно.** Настройки персональные, там же тихие
часы. Вид - обязательный аргумент функций отправки: новая рассылка без вида
не пройдёт миграцию, а значит и мимо настроек не проскочит.

Уведомление никогда не роняет запись: отправка обёрнута в обработчик исключений
и работает асинхронно.

### Настройка на новом окружении

В `.env` нужны `TELEGRAM_BOT_ID` (токен бота), `PUSH_ENDPOINT_URL` и
`PUSH_SHARED_SECRET`. Затем:

```bash
pnpm secrets            # секреты из .env в Vault, с проверкой токена через getMe
```

Переменные окружения Vercel: `VITE_PUBLIC_VAPID_KEY`, `VAPID_PRIVATE_KEY`,
`VAPID_SUBJECT`, `PUSH_SHARED_SECRET`, `SUPABASE_URL`, `SUPABASE_SECRET_KEY`.
Значения - в локальном `.env`.

Получателю Telegram: написать `@userinfobot` за своим id, открыть бота и нажать
«Старт» (без этого Telegram не даёт боту писать первым), вставить id в профиль.

На iOS push работает **только** у приложения, добавленного на экран «Домой».
В обычной вкладке Safari его нет.

Подробности - `wiki/pages/concepts/notification-settings.md`,
`wiki/pages/concepts/telegram-notifications.md`, `wiki/pages/concepts/meal-reminders.md`.

## Миграции идут через CLI, не через MCP

Supabase CLI на машине разработки может быть авторизован под другим аккаунтом,
а MCP-сервер - привязан к другому проекту. Поэтому `scripts/db.ts` всегда ходит
по строке подключения из `.env`, а цель задана явно. Инструменты `mcp__supabase__*`
в этом проекте не используются.
